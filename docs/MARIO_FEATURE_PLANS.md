## Flagpole height bonus

Touching the flag pole now pays out by how high you grabbed it. The pole is measured from the block the player actually touched down to its BASE and up to its TOP, giving a 0-based grab index and the pole's real height; that pair maps to one of five bands (BASE 200, LOW 800, MID 2000, HIGH 4000, TOP 8000 + a 1-Up). A player who limps in on the ground gets 200; one who launches off a TrampolineBlock/SpringPadBlock into the TOP block gets 8000 and an extra life, with the 1-Up sound and a floating score popup at the moment of the grab. The band is recorded at grab time in CourseCompletionService.beginSlide, but the points are added inside CourseScoringService.finishCourse alongside the pip and time bonuses — so the bonus is inside results.finalScore() before ProgressionService.recordClear stores the best score and before the state reset in onComplete. The results screen gains a "Flag bonus" row and the clear message a matching line. The two pole builders in the mod are different heights (CourseComposer builds 8 blocks, CourseStructureService builds 7), so the band is computed from a measured fraction rather than an absolute Y and both read the same.

### Steps

1. Add pole geometry to `FlagPoleBlock` (C:/Dev/PlaneShift/src/main/java/com/studio/planeshift/common/block/FlagPoleBlock.java). Add `public record Grab(int index, int height) {}` and `public static Grab measure(net.minecraft.world.level.BlockGetter level, BlockPos touched)`. Implementation: walk down from `touched` while `level.getBlockState(p.below()).getBlock() instanceof FlagPoleBlock` to find `baseY` (cap the walk at 32 iterations so a griefed column cannot spin); walk up the same way to find `topY`; return `new Grab(touched.getY() - baseY, topY - baseY + 1)`. Do NOT read the PART property to decide the band — the two builders disagree about how many POLE blocks sit between BASE and TOP, and PART alone cannot distinguish pole block 2 of 6 from 2 of 5. `entityInside` is left exactly as it is; it still just calls `CourseCompletionService.beginSlide(player, pos)`.

2. Add the band table to `CourseScoringService` (src/main/java/com/studio/planeshift/server/CourseScoringService.java) as a nested `public enum FlagBand { BASE(200,false), LOW(800,false), MID(2000,false), HIGH(4000,false), TOP(8000,true) }` with `int points()` and `boolean oneUp()`, plus a pure static `static FlagBand of(int grabIndex, int poleHeight)`. Rules, in this order: `poleHeight < 2` -> BASE (a degenerate one-block pole must not read as TOP); clamp `grabIndex` into `[0, poleHeight-1]`; `grabIndex == poleHeight - 1` -> TOP; `grabIndex * 3 >= (poleHeight - 1) * 2` -> HIGH; `grabIndex * 3 >= (poleHeight - 1)` -> MID; `grabIndex > 0` -> LOW; else BASE. Use integer arithmetic, no floating point, and no MC imports inside `of` so the JUnit suite can call it the way it already calls `stompValue`.

### Risks

- FlagPoleBlock.COOLDOWN is 40 ticks and an 8-block slide at 0.2 blocks/tick is ~40 ticks: the cooldown can expire within a tick or two of the slide ending. The only thing preventing a second beginSlide (and a second, lower band) is that PlayState.RESULTS returns false from inCourse(). `putIfAbsent` in recordFlagGrab is a second, independent guard so a regression in the first one costs the player nothing.
- `measure` walks the block column, so a player-placed FlagPoleBlock stacked next to a course pole (the block is in the creative tab via ModItems.FLAG_POLE_ITEM) would extend the measured height. The iteration cap bounds the cost; the band stays monotone, so the worst case is a generous score in a hand-built course, not a crash or a hang.
- `makeMockServerPlayerInLevel()` gives a ServerPlayer whose connection is a stub; `finishCourse` calls `player.sendSystemMessage` and `PacketDistributor.sendToPlayer`. If either throws under the GameTest harness, split the assertion: keep the geometry and band half of the GameTest and assert the ordering by checking `CourseStateAccess.get(p).score()` after `finishCourse` rather than the Results record. Do not weaken the assertion to make it pass (R13).
- The 1-Up on the TOP band and the coin-rollover 1-Up in onComplete's reward block can both fire on the same clear, so a top grab on a 100-coin run yields two lives. That is the arcade behaviour and is intended, but it is worth a deliberate look during play-testing rather than a surprise.
- Adding a component to CourseResultsPayload changes the wire format; a client and server on mismatched builds will fail to decode the results packet. That is normal for this mod's in-development networking and matches how the other payloads have evolved, but it is a hard version break, not a soft one.
- A green build and a green unit suite prove only the band arithmetic. The measurement reads real block states and the ordering claim is about a live player, so runGameTestServer is the part that actually proves the feature (R6).

### Integration

Nothing in course generation changes: CourseComposer still writes BASE/POLE x6/TOP into the CourseCanvas and CourseStructureService still writes its 7-tall variant, so CourseReachability sees the same world it sees today and is told nothing new — no property is asserted to the solver (R13). The band is derived by measuring the placed pole rather than by trusting a constant, which is exactly why the two builders' differing heights do not need to be unified. FlagPoleBlock.entityInside keeps its existing signature, its LAST_TRIGGER/COOLDOWN dedupe and its unconditional `beginSlide` call; the new geometry helper is a static the block exposes, so the block does not gain scoring knowledge and scoring stays in the server service, per the convention that per-player gameplay logic lives under server/. The bonus rides the single existing `addScore(player, bonus)` in `finishCourse`, so the CourseState.MAX_VALUE clamp, the AttachmentType persistence and the HUD sync all keep working unchanged — there is no second write path to the score. `recordClear` and the results payload both read `results.finalScore()`, so both pick the bonus up without their own changes. `TesterService`'s COMPLETE action calls `onComplete` with no recorded grab; the null band yields a zero flag bonus and no life, so the debug path keeps working. The transient FLAG_GRAB map is cleared from the same two places CHAINS and DEFEATED already are, so leaving a course, dying, or logging out cannot carry a band into the next run. No player movement is written per tick and `hurtMarked` usage is untouched — the slide velocity code in ServerEvents is left exactly as found. Shared-mechanism note (R8): the TOP band is only reachable by launching from TrampolineBlock/SpringPadBlock under AirMoveService control, and the slide that follows a TOP grab is long enough to outlast FlagPoleBlock.COOLDOWN — the RESULTS-is-not-inCourse guard in beginSlide is the thing that prevents a re-trigger, and a comment there names it so it is not removed as redundant.


## Spin as a universal verb

The player gets one new key (default X, "Spin"). Pressed on the ground it fires a short 360-degree spin: a symmetric hit around the player that squishes and defeats stompable enemies on both sides at once, trips a walking Koopa into its shell instead of killing it, kicks a parked shell away like a stomp-kick would, and clanks harmlessly off armoured tops. Pressed in the air it spends a single stall — a brief hover with one small upward nudge — that is recharged only by touching the ground, so it reads as a saving throw for a missed jump rather than a second jump. For the length of the spin window the player is also "spin jumping", which is the flag CourseEnemyEntity.resolveStomp already reads to turn a spike-damage stomp into a safe bounce, so the move that already existed in the codebase but could never be triggered becomes reachable on purpose.

### Steps

1. Add `SPIN` to `PlaneShiftKeybinds` (client/PlaneShiftKeybinds.java): a `KeyMapping` named `key.planeshift.spin`, `KeyConflictContext.IN_GAME`, `InputConstants.Type.KEYSYM`, `GLFW.GLFW_KEY_X`, in the existing `CATEGORY`. X is chosen because vanilla leaves it unbound and it is off the number row the player holds during a course. Register it in `ClientModEvents.onRegisterKeyMappings` alongside FORM_ACTION/SWAP_RESERVE/TESTER_MENU. Add `"key.planeshift.spin": "Spin"` to src/main/resources/assets/planeshift/lang/en_us.json next to the other key.planeshift entries.

2. Add `common/network/SpinActionPayload.java`, copied exactly from `ReserveSwapPayload`: a no-field record with `INSTANCE`, `TYPE = new Type<>(PlaneShift.id("spin_action"))` and `STREAM_CODEC = StreamCodec.unit(INSTANCE)`. It deliberately carries no data — direction, ground/air context and cooldown are all server-owned; nothing the client sends may influence what the spin does.

3. Register it in `ModNetworking.onRegisterPayloadHandlers` with `registrar.playToServer(SpinActionPayload.TYPE, SpinActionPayload.STREAM_CODEC, (payload, context) -> context.enqueueWork(() -> { if (context.player() instanceof ServerPlayer p && PayloadRateLimiter.allow(p, PayloadRateLimiter.Action.SPIN)) SpinService.trigger(p); }))`. Add `SPIN(4)` to the `PayloadRateLimiter.Action` enum with a comment saying the 4-tick cost only bounds packet rate for a scripted client and that the real cooldown is SpinService's — the limiter never replaces validation. `PROTOCOL_VERSION` stays "1": adding a payload type does not change any existing wire format.

4. Send it from `ClientEvents.onClientTickPost`, in the same `minecraft.screen == null` block as the existing keys: `while (PlaneShiftKeybinds.SPIN.consumeClick()) ClientPacketDistributor.sendToServer(SpinActionPayload.INSTANCE);`. `consumeClick` is edge-triggered, which is what makes this a press rather than the level-triggered mistake R8 records against the original spin jump.

5. Add `common/course/SpinRules.java` — pure Java, no Minecraft imports, so the decision logic can be unit-tested. Contents: `public enum Outcome { GROUND_ATTACK, AIR_STALL, NONE }`; `public static Outcome resolve(boolean onGround, boolean stallAvailable, int spinTicksRemaining, int groundCooldownRemaining)` returning NONE while `spinTicksRemaining > 0` (no re-entry mid-spin), NONE on the ground while `groundCooldownRemaining > 0`, GROUND_ATTACK on the ground otherwise, AIR_STALL in the air only when `stallAvailable`, NONE in the air otherwise; `public static double stallRise(double currentVelocityY, double measuredRise, double nudge)` returning `Math.max(currentVelocityY, measuredRise) + nudge`; `public static double stallHold(double currentVelocityY, double measuredRise, double hoverSpeed)` returning `Math.max(Math.max(currentVelocityY, measuredRise), hoverSpeed)`. Those last two are the AirMoveService rule written down: a velocity the server sends may never be smaller than the rise the client was just measured to have.

6. Expose the measurement AirMoveService already takes, rather than measuring a second time. In `AirMoveService`, add `public record Measured(double moveX, double moveZ, double rise) {}`, a `private static final Map<ServerPlayer, Measured> MEASURED = new WeakHashMap<>()`, and immediately after the existing `moveX`/`moveZ`/`measuredRise` locals are computed, `MEASURED.put(player, new Measured(moveX, moveZ, measuredRise))`. Add `public static Measured measured(ServerPlayer player)` returning the stored value or `new Measured(0, 0, 0)`. Remove the entry in `forget`. This is load-bearing: `LAST_XZ` and `LAST_Y` are consumed and overwritten inside `tick`, so a second service that measured for itself would either double-book the maps or read a zero delta depending on ordering.

7. Add `server/SpinService.java`, the per-player service, ticked from ServerEvents like every other. State in `WeakHashMap<ServerPlayer, …>`: `SPIN_TICKS` (Integer, the active spin window), `GROUND_COOLDOWN` (Integer), `STALL_AVAILABLE` (Boolean), `STALLING` (Integer, hover ticks left). Constants: `SPIN_ACTIVE_TICKS = 12`, `GROUND_SPIN_COOLDOWN_TICKS = 24`, `SPIN_REACH = 1.6` horizontal and `SPIN_HEIGHT = 0.9` vertical for the hit box, `SPIN_DAMAGE = 10.0F` (the same number as `CourseEnemyEntity.stompDamage()`, so a spin and a stomp kill the same things), `STALL_HOVER_SPEED = -0.02`, `STALL_NUDGE = 0.16`, `STALL_TICKS = 8`.

8. `SpinService.trigger(ServerPlayer)`: return immediately unless `CourseStateAccess.get(player).inCourse()`. Switch on `SpinRules.resolve(player.onGround(), STALL_AVAILABLE.getOrDefault(player, false), SPIN_TICKS.getOrDefault(player, 0), GROUND_COOLDOWN.getOrDefault(player, 0))`. GROUND_ATTACK: set SPIN_TICKS and GROUND_COOLDOWN, play `ModSounds.STOMP` at pitch 1.4 once, call `spinHits(level, player)`. AIR_STALL: set SPIN_TICKS, set `STALLING` to STALL_TICKS, clear STALL_AVAILABLE, play `ModSounds.POWER_UP` at pitch 1.8 once. NONE: do nothing at all — no sound, because a denied input that still makes noise is the level-triggered POWER_UP spam R8 recorded, in a new place.

9. `SpinService.tick(ServerPlayer)`, called once per player tick: decrement SPIN_TICKS and GROUND_COOLDOWN; on `player.onGround()` set `STALL_AVAILABLE` to true and clear `STALLING` (landing is the only recharge); while `SPIN_TICKS > 0` and the level is a ServerLevel, emit `ModParticles.COIN_SPARKLE` every other tick around the player, matching the existing spin-jump trail; while `STALLING > 0` and the player is airborne, apply the stall. The stall write is the only place velocity is touched and it copies AirMoveService verbatim: read `AirMoveService.Measured m = AirMoveService.measured(player)`, build `double y = firstStallTick ? SpinRules.stallRise(player.getDeltaMovement().y, m.rise(), STALL_NUDGE) : SpinRules.stallHold(player.getDeltaMovement().y, m.rise(), STALL_HOVER_SPEED)`, then `player.setDeltaMovement(m.moveX(), y, m.moveZ()); player.hurtMarked = true; player.resetFallDistance();`. Horizontal components come from the measured position delta, never from `getDeltaMovement()`, because hurtMarked sends an absolute velocity packet and writing the server's stale horizontal back out is exactly what destroyed horizontal momentum before.

10. `SpinService.spinHits(ServerLevel level, Player attacker)` — the ground attack, returning an int hit count so a GameTest can assert on it. Take `attacker.getBoundingBox().inflate(SPIN_REACH, SPIN_HEIGHT, SPIN_REACH)` and iterate `level.getEntitiesOfClass(CourseEnemyEntity.class, box)`. Skip anything not `isAlive()` or `fallingFromDrop()` (a dropped enemy is untouchable both ways, which is the existing contract). Per enemy: if it is a `KoopaEntity`, call `koopa.spinKick(attacker)` when it is a parked shell and `koopa.spinTrip()` when it is walking; else if `!enemy.isStompable()`, play `ModSounds.STOMP` at pitch 0.6 and do nothing else — no damage to the enemy and, importantly, none to the player, because the safe-contact half of spin is the whole reason the flag exists; else `enemy.hurtServer(level, attacker.damageSources().playerAttack(attacker), SPIN_DAMAGE)` followed by `enemy.startSquish()`, and on `!enemy.isAlive()` with `attacker instanceof ServerPlayer sp` call `CourseScoringService.awardStomp(sp)`. The box is symmetric, so 'hits enemies either side' needs no direction term. Routing through hurtServer means fire immunity, the squish framework and the pip damage model all behave as they already do.

11. Add two small public entry points to `KoopaEntity`, both documented, neither changing existing behaviour: `public boolean spinTrip()` — returns false if `inShell()`, otherwise calls the existing private `enterShell()` and returns true, so a spin knocks a walker into its shell rather than deleting an enemy whose identity is that it survives being hit; and `public boolean spinKick(ServerPlayer player)` — returns false unless `inShell() && !sliding()`, otherwise calls the existing private `kick(player)` and returns true. `kick` already enforces `KICK_GRACE_TICKS` and `KICK_REACH` and already flattens the launch direction away from the player, so the spin kick inherits every rule the stomp kick has instead of restating them.

12. Wire it into `ServerEvents`: in `onPlayerTickPost`, call `SpinService.tick(player)` on the line immediately after `AirMoveService.tick(player)` — after, because AirMoveService populates the measurement SpinService reads, and because the stall must be the last velocity write of the tick or the hold-jump top-up and wall-slide clamp would argue with it. ### Risks

- Input collision, the R8 failure repeating. Spin is on its own key, but its *state* now overlaps every sneak-bound move: the ground pound and spin jump in AirMoveService, and the pounce dive in CatFormService, all trigger on sneak while airborne. Because isSpinJumping is widened to include the spin window, the pound guard must be widened with it (step 13) or an air stall is converted into a downward slam on the very next tick — which is precisely how the original spin jump was made unreachable. Both SpinService's and AirMoveService's javadoc must name each other and CatFormService explicitly.
- Tick ordering. SpinService reads a measurement AirMoveService takes, and writes the last velocity of the tick. Call it before AirMoveService and the stall reads a stale Measured and is then overwritten by the hold-jump top-up. The ordering is a correctness requirement, not a style choice, and belongs in a comment at the call site in ServerEvents.
- The stall makes courses easier, and CourseReachability must not be told. Extra hang time plus a 0.16 nudge means every gap the solver proved crossable is still crossable; the temptation is to widen generated gaps to account for the stall, which would be asserting a property to the solver and would make the walkability proof describe a game only a player who spends the stall is playing. Nothing in server/gen/ is touched by this feature, deliberately.
- Damage number drift. SPIN_DAMAGE is set equal to CourseEnemyEntity.stompDamage()'s 10.0F so a spin and a stomp kill the same set of enemies. If one of the two is retuned later and the other is not, spin quietly becomes the strictly better opener. Both should carry a comment pointing at the other.
- Koopa surface. Two new public methods on KoopaEntity are the minimum needed and both delegate to existing private code so the kick grace, the kick reach and the shell entry rules cannot drift into a second copy. A future third caller must go through these, not re-derive them.
- Air stall versus the client-side Glider float in PlaneMovementAssists, which is also a descent-limiter and is also on the client. The two stack: a floating Glider that spins gets both. That is acceptable (the float only reduces descent, the stall is once per stint) but it is a combination nobody has flown yet, and it is the first thing to look at if the stall reads as too strong in playtest.
- A green build and a passing suite prove neither half of this works in game (R6). The unit test proves arithmetic; the GameTest proves the ground attack runs under FML's classloader; the stall's packet behaviour is proved only by playtest.

### How it is proved

Two proofs, because the feature has two halves with different failure modes.

(1) Pure logic — src/test/java/com/studio/planeshift/common/course/SpinRulesTest.java (JUnit, no Minecraft on the classpath, same shape as CourseProgressTest/PickupParticlesTest). Cases: `resolve` returns AIR_STALL for (airborne, available) and NONE for (airborne, not available), proving one stall per airborne stint; NONE whenever spinTicksRemaining > 0, so a held key cannot re-enter; NONE on the ground while groundCooldownRemaining > 0; GROUND_ATTACK on the ground at cooldown 0. And the anti-fighting-the-client property, swept over a grid of values including a client-side double jump larger than the server's stale y: `stallRise(currentY, measuredRise, nudge) >= measuredRise` and `stallHold(currentY, measuredRise, hover) >= measuredRise` must hold for every pair, i.e. the value the server is about to send absolutely can never be less than the rise the client was just measured to have. That is the AirMoveService lesson turned into an assertion instead of a comment.

(2) In-game — a `spin_test` GameTest in PlaneShiftGameTests, run by `runGameTestServer` in CI. It sets a stone floor, spawns a GoombaEntity, a walking KoopaEntity and a second KoopaEntity that has already been put into its shell, all inside SPIN_REACH of `helper.makeMockPlayer(GameType.SURVIVAL)` positioned between them, then calls `SpinService.spinHits(helper.getLevel(), player)` and asserts: the Goomba is dead, the walking Koopa now reports `inShell()` and is still alive, the shelled one now reports `sliding()`, and the returned hit count is 3. Run it a second time immediately to assert the shelled Koopa is not re-kicked while sliding. This is why `spinHits` takes `(ServerLevel, Player)` rather than a ServerPlayer — `makeMockPlayer` returns a Player, and a signature a GameTest cannot call is a signature nothing in-game ever proves. It is also the R6 half of the proof: entity spawning, the registry lookups, damage sources and the mod's own enemy classes all run under FML's classloader here and only here.

What neither test covers, stated rather than hidden (R6): the air stall touches ServerPlayer velocity and hurtMarked, which no mock player and no unit test can exercise. It is proved by the pattern it copies verbatim and by a manual playtest — jump into a pit, press X once mid-fall, and check three things: the player visibly hangs and rises slightly, horizontal speed is unchanged across the stall (this is the failure mode the LAST_XZ pattern exists to prevent), and a second press does nothing until after landing.


### Integration

Nothing existing changes behaviour except by widening, and every widening is at a point the codebase already documents. CourseEnemyEntity.resolveStomp is not edited at all — it already reads AirMoveService.isSpinJumping, and this feature simply makes that read reachable for a reason other than the sneak+jump entry, which R8 records as being effectively dead. The old sneak+jump spin jump stays exactly as it is; SPIN_JUMPING is untouched and isSpinJumping becomes an OR of the two sources, so any existing player habit still works. KoopaEntity gains two public wrappers around existing private code and no existing method body changes, so shell grace, kick reach and shell entry keep exactly one implementation each. The two AirMoveService edits are additive: a measurement that was already computed is stored and exposed rather than recomputed (recomputing it in a second service would fight over LAST_XZ/LAST_Y), and the ground-pound condition gains one clause whose absence would reproduce R8. The stall follows the LAST_XZ / measuredRise pattern exactly — horizontal from the measured position delta, vertical never smaller than the measured rise — so hurtMarked's absolute velocity packet agrees with the client instead of overwriting it. Networking follows the existing shape: a no-data C2S payload, a StreamCodec, PROTOCOL_VERSION unchanged since no existing wire format moves, validation and cooldown server-side, and a rate-limiter entry alongside LOAD_COURSE and SHOP_PURCHASE. The keybind sits on a vanilla-unbound key in the mod's existing category with a lang entry and a HUD hint. Course generation and CourseReachability are not touched: the stall only ever makes a proven-walkable course easier, and the solver is never told about it.


## Enemy-versus-enemy and enemy-versus-hazard resolution

Today the only way one enemy can defeat another is KoopaEntity.tickSlide, and it is a 15-line inline loop that hard-codes damage, sound, victim filtering and scoring credit. After this change every "something that is not the player defeats an enemy" path runs through one server-side helper, EnemyClash, with its decision logic in a pure, unit-testable EnemyClashRules. The player sees: a kicked shell still ploughs a line of Goombas and still climbs the score ladder, but it now stops grinding a fake combo against a Thwomp; a Bullet Bill scatters the Goomba line it flies through and pays the ladder to the player whose approach fired the cannon; a Thwomp slamming down crushes anything under it; lava, Munchers and spikes kill enemies that touch them with the mod's own defeat sound, smoke puff and HIT_BURST particles rather than a silent vanilla death; and an enemy that falls onto another bounces off it instead of standing inside it. Every defeat, whatever caused it, now produces identical presentation, because CourseEnemyEntity.die is the single funnel.

### Steps

1. STEP 1 — Add the pure rules class. New file src/main/java/com/studio/planeshift/common/entity/EnemyClashRules.java, final, private constructor, static-only, importing nothing from net.minecraft. This is the piece the unit test covers, following the precedent of PiranhaPlantEntity.extensionFor and CourseScoringService.stompValue (both package-visible pure statics with a JUnit test and no world). Contents: (a) `public enum Aggressor { SHELL, BULLET, CRUSHER, FALLER }` — SHELL is a sliding Koopa, BULLET a Bullet Bill, CRUSHER a descending Thwomp, FALLER any enemy that is merely falling; (b) `public enum Outcome { NONE, DEFEAT_TARGET, BOUNCE_OFF }`; (c) `public enum Hazard { LAVA, MUNCHER, SPIKE }`; (d) `public static Outcome resolve(Aggressor aggressor, boolean targetDefeatableByEnemies, boolean targetAirDropped, double aggressorMinY, double aggressorMaxY, double targetMaxY, double relativeYSpeed)` — SHELL and BULLET return DEFEAT_TARGET when targetDefeatableByEnemies and !targetAirDropped, else NONE; CRUSHER returns DEFEAT_TARGET only when relativeYSpeed < CRUSH_MIN_SPEED (negative, i.e. actually slamming) and targetDefeatableByEnemies, else NONE; FALLER returns BOUNCE_OFF when aggressorMinY >= targetMaxY - LANDING_BAND and relativeYSpeed < LAND_MIN_SPEED, else NONE. Never DEFEAT_TARGET for FALLER — the spec says a falling enemy bounces, it does not kill; (e) `public static double landingBounce(double incomingYSpeed)` returning a clamped positive number (constants FALLER_BOUNCE = 0.32, FALLER_BOUNCE_MAX = 0.42) so a fast faller does not launch to orbit; (f) `public static boolean hazardDefeats(Hazard hazard, boolean fireImmune)` — LAVA returns !fireImmune (this is what keeps the Buzzy Beetle's declared fire immunity meaning one thing in one place), MUNCHER and SPIKE return true unconditionally; (g) `public static int nextChainStep(int step)` returning step + 1, and `public static int clampChainStep(int step)` returning Math.max(0, step), so the caller never hands CourseScoringService a negative. Named constants with javadoc for each, no magic numbers at the call sites.

2. STEP 2 — Add the world-facing helper. New file src/main/java/com/studio/planeshift/common/entity/EnemyClash.java, final, private constructor, static-only, server-side only (every entry point begins `if (level.isClientSide()) return;`). It is the single place that knows how to turn an EnemyClashRules.Outcome into damage, sound, particles and score. Methods to add: (a) `public static int sweep(CourseEnemyEntity aggressor, EnemyClashRules.Aggressor kind, double reach, int chainStep)` — collects victims with `aggressor.level().getEntitiesOfClass(CourseEnemyEntity.class, aggressor.getBoundingBox().inflate(reach), e -> e != aggressor && e.isAlive())`, calls EnemyClashRules.resolve per victim, and on DEFEAT_TARGET calls defeat(victim, aggressor); returns the number defeated so the caller can advance its chain step by that many rather than by one per tick. Uses getEntitiesOfClass on the aggressor's own inflated box, never a BlockPos cuboid, so checkNoRawCuboidScan in build.gradle stays green; (b) `public static void defeat(CourseEnemyEntity victim, CourseEnemyEntity source)` — sets victim.setDefeatCredit(source.defeatCreditOwner(), source.defeatChainStep()) then `victim.hurtServer((ServerLevel) victim.level(), victim.damageSources().mobAttack(source), Float.MAX_VALUE)`. Float.MAX_VALUE rather than KoopaEntity's SHELL_DAMAGE = 20.0F: 20 is a number that happens to exceed a Goomba's 6 HP and happens not to exceed a Thwomp's 30, which is why the current code can hit the same Thwomp forever. Whether a shell can kill a thing is a rules question answered by isDefeatableByEnemies, not a hit-points question; (c) `public static void hazard(CourseEnemyEntity victim, EnemyClashRules.Hazard hazard)` — returns early unless EnemyClashRules.hazardDefeats(hazard, victim.fireImmune()), then hurtServer with the matching vanilla DamageSource (lava(), cactus(), generic()) at Float.MAX_VALUE, with no credit set so a hazard kill scores no combo; (d) `public static void landOn(CourseEnemyEntity faller, CourseEnemyEntity support)` — applies EnemyClashRules.landingBounce to the faller's Y velocity, sets `faller.hurtMarked = true`, calls support.startSquish(), plays ModSounds.STOMP at pitch 0.7F. hurtMarked is correct here and only here: this is a single discrete impulse on a server-owned mob, not a per-tick rewrite of a player's velocity, so the CLAUDE.md warning about hurtMarked fighting the client does not apply — enemies are server-authoritative; (e) `public static void presentDefeat(CourseEnemyEntity victim)` — the ENEMY_DEFEAT sound, the 12-particle CLOUD puff and the 10 HIT_BURST particles currently inlined in CourseEnemyEntity.resolveStomp, lifted here verbatim so a lava death and a stomp death look the same.

### Risks

- Removing SHELL_DAMAGE=20 in favour of a rules-gated lethal hit changes which enemies a shell kills. Anything whose only protection was hit points above 20 now dies unless it overrides isDefeatableByEnemies. Mitigation: audit all twelve CourseEnemyEntity subclasses (Goomba, Koopa, Spiny, BuzzyBeetle, BulletBill, Thwomp, HammerBro, Lakitu, Boo, PiranhaPlant, Bowser) during STEP 3 and set the override deliberately for each rather than by default; Thwomp and Bowser are the two identified as false.
- Overriding die(DamageSource) on CourseEnemyEntity funnels every death, including ones outside this feature — a creative-mode /kill, a fireball, a hammer, despawn-adjacent paths. presentDefeat will now fire for all of them. That is arguably correct (one defeat looks like one defeat) but it is a wider behaviour change than the spec asks for, and it must be checked that die() is not reached during world unload or the sound plays to nobody. Guard presentDefeat behind a level().isClientSide() check and an isAlive/removal-reason check.
- The landing-bounce path in tickWorldContact runs a getEntitiesOfClass every tick for every falling enemy. On a course with a Lakitu raining Spinies this is a handful of small-box queries per tick and is fine, but the early-out ordering in STEP 4 matters: the query must be reached only when the enemy is genuinely airborne and descending, or it becomes a per-enemy-per-tick scan.
- Bullet Bill credit comes from getNearestPlayer at firing time, which in co-op may not be the player the bullet eventually flies past. CourseCoopService exists and this feature does not consult it. Acceptable for a first cut, but it should be named in the commit message rather than discovered later as a scoring inconsistency.
- SpikeBlock currently damages any entity generically. Routing CourseEnemyEntity through EnemyClash.hazard makes spikes instantly lethal to enemies where they previously did 4.0F per touch. If any existing course places a spike where an enemy is meant to walk past unharmed, that enemy now dies on the way. Worth a quick grep of SegmentLibrary and CourseStructureService for spike placements adjacent to enemy spawns before committing.
- A Thwomp crushing enemies pays no score, while a shell and a Bullet Bill do. That is a deliberate design call (a Thwomp is scenery, not the player's doing) but it is the kind of asymmetry a player notices; it belongs in the design notes, not only in a code comment.

### How it is proved

Two proofs, split along the line R6 draws. (1) Pure logic — src/test/java/com/studio/planeshift/common/entity/EnemyClashRulesTest.java, run by `.\\gradlew test`. The load-bearing case is a parameterised sweep asserting EnemyClashRules.resolve(Aggressor.SHELL, targetDefeatableByEnemies=false, ...) returns NONE for every relative speed and every Y offset: that is the exact regression that today lets a sliding shell parked against a Thwomp increment shellCombo once per tick and hand the player a free 1-Up in eight ticks. Second load-bearing case: a sweep over all seven parameters asserting Aggressor.FALLER never returns DEFEAT_TARGET, pinning 'a falling enemy bounces off' as a rule rather than a coincidence of the current damage numbers. (2) Real runtime — the new enemy_clash_test GameTest in PlaneShiftGameTests, run by CI's existing runGameTestServer. ### Integration

Nothing is registered, so ModEntities, ModBlocks, ModItems, ModSounds, ModParticles, ModAttachments and the sounds.json / texture build checks are all untouched — there is no new block, item, entity type, sound, packet or attachment, and therefore no new DeferredBlock/DeferredItem entry and no new CustomPacketPayload. Course generation is not touched at all: CourseCanvas, CourseComposer, CourseWriter and CourseReachability never see this code, and no property is asserted to the reachability solver — the change is entirely runtime entity behaviour after a course exists. Player-facing stomp behaviour is preserved: playerTouch, isStompContact, the four-tick STOMP_COOLDOWN_TICKS, the invulnerableTime=0 pairing, the BOUNCE_HEIGHT attribute lookup and the air-drop grace all keep their current code and comments; the only change to resolveStomp is that its defeat presentation moves into the shared funnel and it sets alreadyScored so the funnel does not pay twice. Per R8, the two features that now share an input are named in the code: resolveStomp (player contact) and CourseEnemyEntity.die (the defeat funnel) both fire on the same entity in the same tick, and resolveStomp is documented as the earlier claim that the funnel defers to via alreadyScored. hurtMarked is used only in EnemyClash.landOn, as a one-shot impulse on a server-authoritative mob — not a per-tick velocity rewrite on a player, so the CLAUDE.md hurtMarked warning is respected. Every entity query is a getEntitiesOfClass on an aggressor's own inflated bounding box; no BlockPos cuboid is iterated, so checkNoRawCuboidScan stays green, and no whole-level per-tick sweep is added — each check is driven from the entity or block that is already ticking.


## Ground pound as an offensive vector: contact defeat, one-tile flip shockwave, three-block stagger

After this change a ground pound is the mod's general-purpose answer to armour instead of a block trigger. While GROUND_POUNDING is set, touching any CourseEnemyEntity resolves as a pound: the enemy is defeated regardless of its ARMOR attribute or its isStompable() override (Spiny, Buzzy Beetle, Bowser excepted by an explicit damage override), and — crucially — the player does not bounce, so the pound continues to the ground. On landing, the existing HitFromBelowBlock.impact call still fires exactly as it does today, and a new shockwave runs alongside it: shelled enemies within one tile (Buzzy Beetle and Spiny; Ant Trooper does not exist in the codebase yet and gets it free via the same hook) flip onto their backs for ~60 ticks, during which they stop patrolling, stop dealing contact damage, and become stompable by the ordinary stomp path; other grounded enemies within three blocks are staggered — frozen and squished — for ~15 ticks. Nothing about course generation, reachability, jump height, scoring, networking or the block dispatcher changes.

## P-meter as a real gauge: fill / hold / drain, synced on CourseState, drawn in CourseHud

While running on the ground in a course, a segmented chevron gauge under the health pips fills over ~40 ticks. Jumping, being bumped, or stopping no longer zeroes it: it holds for 12 ticks and then drains at half the fill rate, so the player can carry speed into a jump and can watch the meter bleed away before they feel it. At full it lights up, plays the existing POWER_UP ping once, and applies a real raised speed ceiling (a transient MOVEMENT_SPEED attribute modifier) plus a small JUMP_STRENGTH modifier instead of the compounding per-tick `v.x * 1.05` multiply that exists today. Leaving the course, dying, or dropping out of full removes both modifiers and zeroes the synced value.

### Risks

- Record arity. `CourseState` gains a 17th component, and the compiler will only catch the call sites — `sanitize`'s two returns and 14 withers in-file, plus CourseService:93. A wither that accidentally passes a literal instead of `pMeter` compiles fine and silently resets the meter on an unrelated event (a coin pickup, a checkpoint). Grep `new CourseState(` after the edit and confirm exactly 19 call sites, all but withPMeter/sanitize/CourseService threading `pMeter` through unchanged.
- STREAM_CODEC field order. `encode` and `decode` are hand-written and independent; appending to one and not the other, or in a different position, desyncs every field after it and produces a garbage HUD rather than a crash. Add both in the same edit, as the last field in each.
- Sync traffic. If someone later syncs the raw 0..80 fill instead of `segments()`, `CourseStateAccess.update` will broadcast the whole CourseState on most ticks of every running player. The 8-step quantisation is load-bearing, not cosmetic; the javadoc on `segments()` must say so.
- Attribute leak on an unusual exit. The cleanup hangs off the `!inCourse()` branch of `MovementRuleService.tick`, which only runs while the player is ticked. A player who disconnects at full P-speed keeps the transient modifier on their in-memory entity; it is transient so it never reaches disk, and `CourseState.sanitize` resets `pMeter` to 0 on load, but confirm `CourseService`/`ModeTransitionService` do not have a path that changes state without a following player tick.
- GameTest mock player. `helper.makeMockPlayer(GameType.SURVIVAL)` is typed as `Player` at the existing call site; if it is not a `ServerPlayer` in this mapping the test will not compile, and a mock with a stub connection may throw inside `player.syncData`. Check the signature first; fall back to `makeMockServerPlayerInLevel`, and if sync on a mock is genuinely unsafe, narrow the GameTest to the attribute-modifier lifecycle (the environment-sensitive half) and leave the value math to PMeterTest — do not weaken the assertion to make it pass.
- Feel regression. Removing the `v.x * 1.05D` multiply changes how P-speed feels immediately, and 0.35 ADD_MULTIPLIED_TOTAL on top of courseRunBoost 0.9 is a guess sized off the existing config comments, not a measurement. Per R6 this needs one actual in-game run before it is called done — a green build and a passing GameTest prove the modifier is applied, not that the speed is right.

### Integration

The meter reuses the existing seams rather than adding any. `CourseState` already carries synced run values (score, coins, pips) and already has a precedent for a field excluded from the persistence codec (`transition`), so `pMeter` follows that shape exactly and no new packet, payload or attachment is introduced. `CourseStateAccess.update` already skips the sync when the snapshot is unchanged, which is why only the 0..8 segment count crosses the wire and not the raw 0..80 fill — quantising means at most eight re-syncs per fill instead of one per tick, and the HUD is segmented anyway, so nothing is lost. Attribute ownership is the one place this could collide: `MOVEMENT_SPEED` is already written by `CourseMovementService` (planeshift:course_run_base), `RoleService` (planeshift:role_run) and `ModEffects` (planeshift:frozen_move, star_power); `JUMP_STRENGTH` by `CourseMovementService`, `RoleService` and three ModEffects. The P-speed modifiers therefore take their own Identifiers and use ADD_MULTIPLIED_TOTAL, which applies after every ADD_VALUE and ADD_MULTIPLIED_BASE contribution, so the course baseline and the role tuning both keep their stated meaning and the P-speed bonus is a clean percentage of whatever the player currently has. They are transient, so nothing reaches the save. Per R8, the code must name its input relationships in comments: the meter reads `isSprinting()`, which no other feature in the codebase reads (verified by grep across src) — the sneak-sharing hazard R8 describes lives in `AirMoveService` and is untouched here; but the meter does share the *position measurement* with the skid detector in the same method, so the reorder must keep `SMOOTH_VEL_X` updated at the end of the skid block and must not recompute `LAST_X` twice. `CourseReachability` is deliberately not told anything: its `MAX_RISE = 4` and `REACH_BY_RISE` are a pessimistic model of the baseline arc and the P-speed jump bonus only widens the margin above it, so the constants stay as they are — per R13, never assert a new capability to the validator.


## Safe introductions: a mechanic's first appearance cannot kill

Today CourseComposer only refuses to place a difficulty>=3 segment whose mechanic is untaught; the segment that actually does the teaching is still free to be a bottomless pit (SINGLE_GAP, DOUBLE_GAP, STAGGERED_GAPS all cut the floor away and leave nothing under it, and in LAVA GenContext.pitFloor puts lava at floorY-4), or a carpet of Munchers (MUNCHER_PIT_HOP, difficulty 2, is a legal introducer of both GAP and UNSTABLE). ### Risks

- Putting Blocks.LAVA and COURSE_MAGMA_BLOCK into the shared hazard set makes CourseReachability strictly stricter, and a LAVA or UNDERGROUND course whose route currently walks over lava will start reporting UNREACHABLE in the existing everyCourseIsWalkable sweep. That is a true positive of the R4 kind — a course that was only completable by taking damage — and the fix is the course, never the hazard set. Run the sweep before and after and record the delta rather than discovering it later.
- INTRO_NET_DROP is tied to CourseReachability.MAX_RISE and REACH_BY_RISE. If someone later retunes the jump model downward, the climb out of a net silently becomes impossible and the only thing that catches it is everyIntroductionIsSurvivable. Say so in a comment on the constant at both ends.
- R6: a green sweep proves the geometry, not the feel. Nothing here has been walked. The net is a visible floor three blocks down inside a pit and it will read as one — the pit of an introducing SINGLE_GAP will look shallower than the same segment later in the course. That may be exactly right (Mario introduces over ground) or may read as the generator having run out of ideas. It needs a play-test before anyone calls it done, and if it looks wrong the answer is to make the net read as intentional (theme accent, a coin line at net level) rather than to delete it.
- Composition gains a record component. Any future code that pattern-matches or destructures it breaks; today there are none, but the constructor is now six-wide and easy to mis-order since three of the components are ints.
- CourseSafety.check runs one BFS per netted column. Without the stands() caching step it is O(columns x course area) and will make the 6 x 5 x 6 x 25 sweep unpleasantly slow. The caching step is not optional polish.
- MUNCHER_PIT_HOP as the introducer of UNSTABLE loses its Munchers entirely, which leaves a fairly empty segment. That is the correct outcome for a first appearance but means the mechanic is genuinely not demonstrated there — the player meets 'stepping stones' rather than 'stepping stones over teeth'. If that reads as hollow, the better fix is to exclude MUNCHER_PIT_HOP from being an introducer and let a gentler UNSTABLE segment do the teaching, not to weaken the netting.

### How it is proved

`CourseIntroductionSafetyTest.everyIntroductionIsSurvivable` — a pure JUnit test, no running game, sweeping all 6 CourseTheme values x difficulty 0..4 x lengths {96,144,180,224,240,720} x 25 seeds (4,500 courses). For every `CourseComposer.Introduction` in every composition it calls `CourseSafety.check`, which asks `CourseReachability` where a player falling in each column of that segment lands, that the landing exists and is not a hazard surface, that the drop is within the fall-damage budget, and that a BFS from that landing reaches the segment's exit column. It fails by accumulating and printing the theme, difficulty, length, seed, segment id and the exact fatal column, so a failure reproduces without rerunning the sweep. To confirm the test is not vacuous, temporarily stub `netIntroduction` to return without writing anything: it must fail on the first pitted introduction in a bottomless theme, and must fail in LAVA on the lava at floorY-4.


### Integration

Nothing outside server/gen changes. CourseStructureService.java:103 constructs the Composition through `CourseComposer.compose(...)` and only reads `canvas()` and `segmentIds()`, so the added record component compiles untouched; CourseWriter needs no change because its clear corridor is already sized off `canvas.minY() - 4` rather than a constant, so a net three blocks under the design floor is cleared and rewritten correctly. No block, item, entity, packet, attachment or service is added, so no registry, no networking, no persistence and no client code is involved — this is composition logic only, which is why it is provable in a plain JUnit test with no running game.

Segment authorship is respected: `netIntroduction` runs after `Segment.build` and only ever touches columns where the segment left no floor at the design height, so a QUESTION_ROW or a BRICK_WALL introducing BLOCKS is not modified at all and its block count does not move. The one place it overwrites authored geometry is MUNCHER_PIT_HOP's Muncher row, and that is the point of the feature rather than a side effect. The net is strictly additive to reachability — it adds stands below the design floor and deletes only hazards — so `everyCourseIsWalkable` cannot regress through it, and `nettingOnlyAddsRoutes` states that as a test rather than leaving it as an argument.

R8, the features sharing an input. Three things read the same canvas and the same Tag set and must be named here. (1) `CourseComposer.populate`, the roaming enemy pass, places ambient mobs on the design floor using the `floorAt` map, which this change does not touch — but it means a netted introduction can still contain a roaming Goomba. That is deliberate and the boundary is worth stating plainly: this feature guarantees the *terrain* of an introduction is not lethal, not that nothing in it can hit you. Making populate respect introductions would gut `coursesAreInhabited` on a 96-block course, where the introductions are most of the level. Enemy-contact lethality on a first appearance is a separate feature and should not be smuggled in here. (2) `CourseComposer.placeStarCoins` sites a coin above the middle of the hardest segments; an introduction is by construction difficulty <= 2, so the two rules cannot collide, but both now read the placed-segment list. (3) The older hand-built path in `CourseStructureService` (the donut_bridge / teaching-version comments around lines 275-320) is a parallel course generator that does not go through CourseComposer at all and gains none of this. It should either be pointed at the composer or explicitly documented as legacy; silently having two teaching rules is how the next person concludes the guarantee holds everywhere when it holds in one of two systems.

R13: `CourseSafety` never tells `CourseReachability` anything. It asks `isStand`, `landingBelow` and `search` and reports what they say. The one number it owns is `maxSafeFall`, and that is a fall-damage question the solver has no opinion about.
